# Anthropic《Building effective agents》：从简单模式开始，而不是一上来搭复杂 Agent

来源：https://www.anthropic.com/engineering/building-effective-agents

原文类型：技术指导文章。  
主轴：先判断是否真的需要 agentic system，再从增强型 LLM、可组合 workflow，到更自主的 agent 逐步增加复杂度；每一步都要用任务约束、评估结果、成本与可控性来决定是否值得。

一句话概括：

> Anthropic 的建议不是“尽量做强大的 Agent”，而是先用最简单的 LLM 调用解决问题，只有当任务需要更高性能、更多灵活性或无法预先写死路径时，才逐步引入 workflow 或 agent，并用清晰工具接口、可观察规划、评估与护栏来控制成本和错误。

## 1. 文章反对的不是 Agent，而是过早复杂化

Anthropic 开篇说，他们过去一年和许多不同行业的团队一起构建 LLM agents，看到最成功的实现往往不是复杂框架或专门库，而是简单、可组合的模式。

这决定了全文的语气：它不是一篇“Agent 终于来了”的宣传文，也不是把所有 LLM 应用都包装成 Agent 的概念文。它真正关心的是工程判断：什么时候简单调用足够，什么时候需要工作流，什么时候才值得让模型自己规划和调用工具。

原文给出的基本原则很直接：构建 LLM 应用时，应先寻找最简单可行的方案，只在需要时增加复杂度。很多应用只要把单次 LLM 调用做好，再配合检索和上下文示例，就已经足够。

## 2. 先分清 workflows 和 agents：路径写死，还是模型自己决定

原文把各种“带有代理性质”的系统统称为 agentic systems，但在架构上区分两类：

- Workflows：LLM 和工具通过预先定义好的代码路径被编排。系统的流程主要由开发者写定。
- Agents：LLM 动态决定自己的流程和工具使用方式，并控制如何完成任务。

这个区分很关键，因为它影响后面的所有选择。workflow 更适合定义清楚、希望稳定一致的任务；agent 更适合需要灵活性、需要模型在较大空间里做决策的任务。两者不是高级与低级的简单排序，而是不同约束下的工程选择。

因此，是否使用 agentic system，本质上是在性能、灵活性、延迟、成本和可控性之间做取舍。复杂系统可能提升任务表现，但通常会带来更高延迟和成本；自主性越强，错误累积的风险也越高。

## 3. 框架能帮你开始，但也可能遮住真正的问题

原文提到了一些框架和工具，例如 Claude Agent SDK、AWS 的 Strands Agents SDK、Rivet、Vellum。它们能简化调用 LLM、定义和解析工具、串联调用等底层任务，让开发者更快上手。

但 Anthropic 同时提醒：框架也会增加抽象层，遮住底层 prompt 和 response，使调试变难；它们还可能诱导团队在简单方案足够时继续加复杂度。

所以文章建议开发者从直接使用 LLM API 开始。很多模式只需要几行代码就能实现。即使用框架，也要理解框架底下到底做了什么，因为对底层机制的错误假设，是客户常见的出错来源。

这不是反框架，而是把框架放回正确位置：它可以是加速器，但不应该替代对系统行为的理解。

## 4. 基础构件：增强型 LLM 才是后面所有模式的起点

在进入各种 workflow 之前，原文先定义了基础构件：augmented LLM，也就是带有检索、工具、记忆等能力增强的 LLM。

Anthropic 强调，现在的模型已经可以主动使用这些能力：自己生成搜索查询、选择合适工具、判断要保留哪些信息。真正需要重点设计的地方有两个：

- 这些能力要贴合具体用例；
- 它们要为 LLM 提供清晰、文档完善、易使用的接口。

原文提到 Model Context Protocol，作为一种把第三方工具生态接入模型的方式。但文章的重点并不是某个协议本身，而是：后续所有 workflow 和 agent，都假设每次 LLM 调用可以访问这些增强能力。工具、检索和记忆不是装饰，而是系统能否可靠工作的基础界面。

## 5. Prompt chaining：把一个难任务拆成固定步骤

第一种 workflow 是 prompt chaining：把任务拆成一串步骤，每次 LLM 调用处理上一步的输出。开发者还可以在中间步骤加入程序化检查，也就是原文图里的 gate，确认流程没有跑偏。

它适合任务可以清楚拆成固定子任务的场景。代价是延迟变高，因为要多次调用模型；收益是每次调用面对的问题更小，准确性可能更高。

原文给了两个例子：

- 先生成营销文案，再翻译成另一种语言；
- 先写文档大纲，检查大纲是否满足标准，再基于大纲写完整文档。

这里的判断标准不是“多步就更高级”，而是：任务是否真的能干净地拆成固定步骤。如果不能，硬拆反而会增加脆弱性。

## 6. Routing：先分类，再交给专门路径处理

第二种 workflow 是 routing：先把输入分类，再导向专门的后续任务。这样可以把不同类型的问题分开优化，避免一个通用 prompt 为了兼顾所有输入而互相拖累表现。

它适合存在清晰类别、并且分类可以准确完成的复杂任务。分类可以由 LLM 完成，也可以由传统分类模型或算法完成。

原文举了两个例子：

- 客服场景中，把一般问题、退款请求、技术支持导向不同流程、prompt 和工具；
- 把简单常见问题交给更小、更省成本的模型，把困难或少见问题交给能力更强的模型，以平衡效果和成本。

Routing 的核心不是“多一个分类器”，而是把关注点分离：不同输入类型拥有不同处理策略，系统才更容易调优。

## 7. Parallelization：并行不是为了炫技，而是为了速度或置信度

第三种 workflow 是 parallelization：让多个 LLM 调用同时处理任务，再用程序聚合结果。原文区分了两种形式：

- Sectioning：把任务拆成互相独立的子任务并行执行；
- Voting：对同一任务运行多次，获得多样输出或多角度判断。

它适合两类情况：一是子任务可以并行以节省时间；二是需要多个视角或多次尝试来提高结果可信度。

原文特别指出，对于有多个考量因素的复杂任务，让不同 LLM 调用分别关注不同方面，通常比让同一个调用同时处理所有事情更好。

例子包括：

- 一个模型处理用户请求，另一个模型同时筛查不当内容或请求；
- 自动化评估中，不同 LLM 调用分别评价模型表现的不同方面；
- 多个 prompt 审查代码漏洞；
- 多个 prompt 判断内容是否不合适，并通过不同投票阈值平衡误报和漏报。

Parallelization 的价值来自任务结构，而不是来自“并行”这个形式本身。

## 8. Orchestrator-workers：当子任务无法预先写死，就让中心模型分派工作

第四种 workflow 是 orchestrator-workers：一个中心 LLM 动态拆解任务，把子任务分派给 worker LLM，再综合结果。

它看起来和 parallelization 相似，但关键区别在于灵活性。parallelization 的子任务通常是预先定义好的；orchestrator-workers 的子任务则由 orchestrator 根据具体输入动态决定。

这适合无法提前预测子任务数量和形态的复杂任务。原文用编码举例：一次复杂代码修改会涉及多少文件、每个文件要怎么改，往往取决于具体任务。搜索任务也类似，可能需要从多个来源收集和分析信息，哪些来源有用并不总能预先确定。

这个模式的价值在于把“拆任务”本身交给模型处理。但它也意味着系统更依赖模型的判断，因此更需要清晰边界、可观察过程和后续评估。

## 9. Evaluator-optimizer：让一个模型生成，另一个模型反馈

第五种 workflow 是 evaluator-optimizer：一个 LLM 生成回答，另一个 LLM 评估并给出反馈，系统在循环中迭代改进。

原文认为，它适合两个条件同时存在的场景：

- 有清晰评估标准；
- 迭代改进能带来可衡量价值。

判断是否适合还有两个信号：如果人类给出反馈后，LLM 的回答确实能明显变好；并且 LLM 自己也能提供这种反馈，那么这个模式就可能有效。原文把它类比为人类写作者打磨文稿的过程。

例子包括文学翻译和复杂搜索。翻译中，初稿可能漏掉微妙语气，评估模型可以给出有用批评；复杂搜索中，评估模型可以判断是否还需要继续搜索和分析。

这个模式的关键不是“循环越多越好”，而是评估标准是否足够清楚，改进是否真的可见。

## 10. Agents：适合开放任务，但必须从环境拿到真实反馈

当模型能力成熟到可以理解复杂输入、推理规划、可靠使用工具并从错误中恢复时，更自主的 agents 才开始在生产中出现。

原文描述的 agent 流程是：它从用户命令或互动讨论开始，明确任务后独立规划和执行；过程中可能回到人类那里获取更多信息或判断；每一步都要从环境获取 ground truth，比如工具调用结果或代码执行结果，用来评估进展；遇到检查点或阻塞时可以暂停请求人类反馈；任务完成后结束，也可以用最大迭代次数等停止条件保持控制。

Anthropic 特别提醒：agents 能处理复杂任务，但实现往往并不神秘。它们通常只是“LLM 基于环境反馈循环使用工具”。正因为如此，工具集和工具文档的设计就非常重要。

Agent 适合开放问题：步骤数难以预测，固定路径无法硬编码，并且开发者对模型决策有一定信任。它的自主性适合在可信环境中扩展任务，但代价是成本更高，也更容易出现错误累积。因此原文建议在沙盒环境中充分测试，并配置合适护栏。

## 11. 两个落地场景：客服和编程为什么特别适合

在附录中，Anthropic 提到两个他们从客户实践中看到价值较高的应用：客服和编码 agents。

客服之所以适合，是因为它天然结合了对话和行动：用户通过对话描述问题，系统需要访问客户数据、订单历史、知识库，并可能执行退款、更新工单等操作。它还有比较明确的成功标准：用户定义的问题是否被解决。一些公司甚至采用按成功解决计费的模式，显示出对 agent 效果的信心。

编码 agents 适合的原因则不同：代码方案可以通过自动化测试验证，agent 可以基于测试结果迭代，问题空间相对结构化，输出质量也更容易客观衡量。Anthropic 提到，他们自己的 agent 已经可以仅基于 pull request 描述来解决 SWE-bench Verified 中的真实 GitHub issue。但原文也强调，自动化测试只能验证功能，是否符合更广泛的系统要求仍需要人类审查。

这两个例子共同说明：适合 agent 的任务通常不仅要能对话，还要能行动；不仅要开放，还要有反馈环和成功标准；不仅要自动化，还要保留有意义的人类监督。

## 12. 工具提示工程：ACI 要像 HCI 一样认真设计

附录 2 讨论工具设计。Anthropic 的观点是：工具定义和规格应该像整体 prompt 一样被认真做提示工程。

同一个动作可以有多种格式。例如文件编辑可以写 diff，也可以重写整个文件；结构化输出可以放在 Markdown，也可以放在 JSON。对软件工程师来说，这些格式可能可以无损转换，但对 LLM 来说难度差异很大。写 diff 要提前知道 chunk header 里的行数变化；把代码放进 JSON 则要处理换行和引号转义。

原文给出的工具格式建议包括：

- 给模型足够 token 先思考，避免它过早把自己写进死角；
- 格式尽量接近模型在互联网上常见的文本形式；
- 避免让模型承担大量格式开销，比如精确数上千行代码，或给大段代码做字符串转义。

文章还提出一个类比：人们会为 human-computer interface 投入很多精力，也应该为 agent-computer interface 投入同样多精力。好的工具定义应该包含示例用法、边界情况、输入格式要求，以及和其他工具的清晰边界。

原文给了一个很具体的经验：在构建 SWE-bench agent 时，他们花在优化工具上的时间甚至超过整体 prompt。模型使用相对路径的工具时，如果 agent 已经离开根目录，就容易犯错；他们把工具改成总是要求绝对路径后，模型就能稳定使用。

## 13. 可复制的工程判断清单

如果把原文压成一份可执行清单，大致是这样：

1. 先问：单次 LLM 调用，加上检索和上下文示例，是否已经足够？
2. 如果不够，再问：任务能否拆成固定步骤？能的话考虑 prompt chaining。
3. 如果输入类型差异明显，且能可靠分类，考虑 routing。
4. 如果任务可拆成独立部分，或需要多视角提高置信度，考虑 parallelization。
5. 如果子任务数量和形态无法预先确定，考虑 orchestrator-workers。
6. 如果有清晰评估标准，且反馈能让结果可衡量地变好，考虑 evaluator-optimizer。
7. 如果任务开放、步骤不可预测、固定路径写不出来，并且能承受更高成本与风险，才考虑更自主的 agent。
8. 无论用哪种模式，都要持续评估效果；只有当复杂度能明确改善结果时，才继续增加复杂度。
9. 对 agent，必须设计好工具接口、工具文档、环境反馈、停止条件、检查点和人类审查边界。
10. 使用框架可以，但不要让抽象层遮住 prompt、response、工具调用和错误来源。

## 14. 不要误读这篇文章

第一，不要把它读成“复杂框架没用”。原文承认框架能降低上手成本，只是提醒生产系统需要理解底层代码和抽象代价。

第二，不要把它读成“Agent 总是比 workflow 高级”。workflow 在定义清楚的任务上更可预测、更一致；agent 适合需要灵活决策的开放任务。

第三，不要把它读成“只要加工具就是 agent”。原文的基础构件是 augmented LLM，而 agent 的区别在于模型能动态指导自己的流程和工具使用。

第四，不要忽略成本和延迟。agentic systems 往往是用成本和延迟换任务表现，是否值得要由具体任务和评估结果决定。

第五，不要把工具设计当成附属工作。原文在附录中反复强调，工具格式、参数名、文档、示例、边界和防错设计，会直接影响模型是否能可靠完成任务。

## 15. 原文脉络备注

- 开头：成功实现通常来自简单、可组合模式，而不是复杂框架。
- “What are agents?”：区分 workflows 和 agents，前者走预设代码路径，后者由 LLM 动态决定流程和工具使用。
- “When not to use agents”：先找最简单方案，只在需要时增加复杂度。
- “When and how to use frameworks”：框架有助上手，但可能遮蔽底层 prompt 和 response，生产中要理解底层实现。
- “The augmented LLM”：检索、工具、记忆是 agentic systems 的基础构件。
- 五种 workflow：prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer，各自对应不同任务结构和取舍。
- “Agents”：agent 适合开放问题，但需要环境真实反馈、停止条件、沙盒测试和护栏。
- 附录 1：客服和编码 agents 的共同点是对话加行动、成功标准、反馈环和人类监督。
- 附录 2：工具提示工程和 ACI 设计会显著影响 agent 可靠性，甚至可能比总体 prompt 更值得投入。

## 最终结论

Anthropic 这篇文章的核心不是给开发者一套炫目的 Agent 架构，而是给出一套逐步加复杂度的控制模型：从简单 prompt 开始，用评估证明哪里不够，再选择恰当 workflow；只有当任务开放到无法写死路径，并且系统能通过工具结果、测试、检查点和人类反馈控制风险时，才把更多决策交给 agent。真正有效的 agentic system，不是最复杂的系统，而是在任务约束下刚好足够、可观察、可调试、可维护的系统。
